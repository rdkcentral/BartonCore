## Context

The `sbmd-runtime-observability` capability (archived change `2026-07-30-sbmd-observability-instrumentation`) instrumented the SBMD JS runtime for the first time: heap gauges, handler invocation timing/outcome, driver load cost, deferred-operation lifecycle, and GC activity (behind `BCORE_SBMD_GC_INSTRUMENTATION`, requiring mquickjs patch `0003`). That change's own Non-Goals and Open Questions flagged several things as deliberately deferred: per-device-instance heap cost ("not tractable — the JS arena has no per-device partitioning"), intra-invocation peak heap (approximation deemed unreliable), and two integration tests (9.6 `sbmd.deferred.timeout`, 9.7 `sbmd.deferred.max_depth`) that needed new test-only driver infrastructure. What it did not do — because it was scoped to instrumentation, not characterization — was answer the two questions that motivate this change: **what does SBMD actually need in terms of memory/CPU resources at realistic scale, and does its behavior at that scale expose any implementation defect?**

This change's primary goal is answering those two questions with real data: a report-driven characterization test suite exercising SBMD under single-device, 20-concurrent-device, 5-distinct-concurrent-driver, and 100-registered-driver workloads. The suite's report (`sbmd_metrics.txt` / `.json`) is regenerated fresh on every run and is not itself a checked-in artifact — the deliverable is the *capability* to produce trustworthy, current findings on demand, not a point-in-time snapshot that would go stale the moment someone re-runs it against different code or a different environment. Getting there required the metric corrections and DEBUG_GC tooling documented below, but those were the *means*, not the goal: exercising the existing instrumentation under the very workloads this change needed to characterize surfaced that a few metrics were unsound or incomplete for exactly the questions being asked of them. `sbmd.driver.load.heap_bytes` (a per-driver before/after heap delta) could read negative when a GC compaction landed mid-load; `sbmd.js.heap.peak_bytes` missed transient spikes that the compacting GC reclaimed before the next sample; and no metric could separate a genuine retained-memory leak from ordinary GC-driven churn under a lazy compacting GC — which is precisely the distinction a resource-envelope characterization needs to draw. Those had to be fixed before the scale data could be trusted; the test infrastructure (concurrent multi-device, heterogeneous multi-driver, and driver-count-scaling scenarios; a graded consolidated report; and DEBUG_GC build-flip automation) is what actually produced the characterization.

**Reconciling the deferred work.** Of the archived change's explicitly deferred items:
- Tasks **9.6** (`sbmd.deferred.timeout` integration coverage) and **9.7** (`sbmd.deferred.max_depth` integration coverage) are effectively done: the multi-device and heterogeneous-driver scenarios in this change both deliberately trigger both conditions as part of their fault-injection phase and assert the counters increment and `sbmd.deferred.in_flight` recovers to zero.
- Per-device-instance heap cost (a stated Non-Goal, "not tractable") is now empirically characterized rather than structurally solved: a device-count sweep shows the post-GC `live_bytes` floor is flat across 1–20 devices of the same driver (slope ≈ 0) — durable per-device state lives in the C++ device-service layer, not the JS arena, so SBMD-runtime heap cost genuinely does not scale with device count. This is a measurement, not an attribution capability; see Non-Goals below for what remains genuinely open.
- Intra-invocation peak heap and the `JS_MEMUSAGE_WALK_HEAP` open question are substantially superseded by `sbmd.js.heap.live_bytes` and the GC-start peak-candidate capture added here — both approaches read `heap_used` at GC boundaries rather than attempting an unreliable intra-call approximation.
- Runtime-configurable heap-sample period, `deviceId`/fleet attributes, explicit-GC production call sites, and swapping the test-only deferred driver for a production one remain open and are unaffected by this change.

**Note on the main spec.** `openspec/specs/sbmd-runtime-observability/spec.md` was already hand-edited (ahead of the normal propose → apply → archive → sync flow) to drop the `sbmd.driver.load.heap_bytes` requirement and its scenario when that metric was removed from code. This change's delta spec therefore does not include a `REMOVED Requirements` block for it — there is nothing left in the main spec to remove — but the removal is recorded here in the proposal and design for a complete history. The delta spec covers only the parts of the main spec not yet reconciled with code: the `peak_bytes` GC-start capture, and the three entirely new requirements (`live_bytes`, `registration.total_ms`, `bundle_load_ms`, and the GC-instrumentation compile guard).

## Goals / Non-Goals

**Goals:**
- Answer, with data, whether SBMD's JS-runtime resource footprint (retained memory, GC pressure, handler latency) scales with commissioned-device count, with the number of *distinct* concurrently active drivers, and with the total registered-driver count.
- Determine, from that same data, whether SBMD's behavior at scale exposes any product-code defect (a leak, an exception, a correctness failure under concurrency, a broken deferred-operation safety mechanism) — as opposed to a defect in the test/observability layer itself.
- (Means, not ends) Make `sbmd.js.heap.peak_bytes` capture transient spikes the compacting GC would otherwise hide from it, and provide a heap metric (`sbmd.js.heap.live_bytes`) capable of showing a genuine retained-memory leak — both needed before the scale data above could be trusted.
- (Means, not ends) Remove the unsound `sbmd.driver.load.heap_bytes` metric, add driver-registration/bundle-load timing visible on every build, and turn a silent opaque link failure into a clear compile-time error — all in service of getting trustworthy numbers.
- (Means, not ends) Remove the manual, undocumented mquickjs rebuild previously required to compare DEBUG_GC-on vs DEBUG_GC-off magnitudes, so the scale scenarios could run under production-representative GC behavior on demand.

**Non-Goals:**
- Per-driver retained-memory *attribution* in a mixed, production workload. The shared 1 MiB JS context has no per-allocation ownership tracking, so a rising `live_bytes` floor cannot be attributed to a specific driver when several are active at once; see Non-Goals below for the full statement of this gap.
- A persisted, continuously-updated per-`(driver, op_type)` `heap_delta` regression baseline (as opposed to the absolute per-series ceiling this change does add).
- Any demand-side / throughput / saturation metric for the shared single-threaded JS engine.
- Rate-windowed or cross-run-trend metrics; every metric here remains cumulative-since-init and every report run is a fresh, independent snapshot.
- Shipping `BCORE_SBMD_GC_INSTRUMENTATION` (and mquickjs patch `0003`) to the production gateway build — an open product decision, unaffected by the compile-time guard added here.

## Decisions

### Decision 1: `live_bytes` samples at GC end, `peak_bytes` samples at GC start — same callback, opposite purpose

Both new/changed heap signals are read from the *same* `JS_SetGCCallback` invocation (`MQuickJsRuntimeMetrics::GCCallback`), which already fires at both GC start (`is_end == 0`) and GC end (`is_end == 1`) for the existing `sbmd.js.gc.count` / `sbmd.js.gc.duration_ms` instrumentation:

- **At GC start** (`is_end == 0`), `heap_used` is at its pre-compaction maximum for that cycle — the only point at which a transient spike (e.g. driver-loading churn) is observable before the GC that is about to fire reclaims it. This is folded into `sbmd.js.heap.peak_bytes` via `RecordPeakCandidate()`, which only advances the gauge if the new reading exceeds the recorded peak (preserving its high-water-mark contract).
- **At GC end** (`is_end == 1`), `heap_used` has just been compacted — this is the true retained live set with all transient garbage reclaimed. This is recorded as the new `sbmd.js.heap.live_bytes` gauge.

**Why not a separate sampling mechanism for either?** The GC callback already runs on every cycle while the JS mutex is held, at exactly the two moments (pre- and post-compaction) that matter for these two questions. Piggybacking on it costs one extra `JS_GetMemoryUsage` call per GC phase — negligible next to the GC cycle itself — versus standing up an independent sampler that would need its own synchronization with the mutex and its own GC-boundary detection.

**Why is `live_bytes` opportunistic (no forced GC)?** An earlier attempt at a similar goal — `sbmd.driver.load.heap_bytes`, a raw before/after `heap_used` delta bracketing driver load — was fixed at one point by *forcing* a GC before and after the measurement window, which made the number sound but also suppressed the very peak (`peak_bytes`) that other tests depend on for honesty about arena pressure. `live_bytes` avoids that trade-off entirely by never forcing a collection: it only ever reports what the engine's own lazy GC schedule already produced. The cost is that under `DEBUG_GC off` (production-representative, lazy GC), `live_bytes` samples are sparse — it is genuinely absent until the first GC fires. Every consumer (report grading, pytest assertions) treats its absence as a skip/`info` condition, never a failure.

### Decision 2: Remove `sbmd.driver.load.heap_bytes` outright rather than patch it again

The metric was already patched once (bracketing the measurement with a forced GC) to eliminate negative readings, but that fix contaminated `peak_bytes` (as above) and only reduced the retained-footprint question to a static, ~6%-of-arena number that was not decision-driving. Per-driver retained footprint and honest transient-peak reporting are mutually exclusive within a single startup measurement approach; this change keeps peak honesty and drops the metric rather than re-patch it a second time. `sbmd.driver.load.duration_ms` (timing only, no heap read) is unaffected and remains the per-driver load-cost signal.

### Decision 3: `registration.total_ms` and `bundle_load_ms` are unconditional, unlike the GC-boundary metrics

Unlike `live_bytes`/`peak_bytes` (which depend on `BCORE_SBMD_GC_INSTRUMENTATION`), `sbmd.driver.registration.total_ms` and `sbmd.driver.bundle_load_ms` are plain `steady_clock` timings gated only by the base `BCORE_SBMD_METRICS` flag — no patched mquickjs API is required. This matters because they are the metrics that first exposed the DEBUG_GC-inflated driver-load-time story (~2.4 s under DEBUG_GC on vs ~20 ms off for the same 13 drivers): they needed to be available in every build, including a production-style build with GC instrumentation disabled, to be trusted as a genuine boot-cost signal rather than a dev-only diagnostic.

### Decision 4: Per-series (not scenario-average) grading for `heap_delta_bytes`

The report originally graded `sbmd.handler.heap_delta_bytes` on the scenario-wide average against a flat threshold. Once the suite added a scenario that exercises several *distinct* drivers at once (heterogeneous multi-driver), that average produced a false positive: the mix of a cheap `light` write (928 B) and a heavier `thermostat` write (2632 B) pushed the average above the threshold even though every individual series was healthy and flat. Grading is now per-`(driver, op_type)` series maximum against an arena-scaled ceiling. This is deliberately an absolute-ceiling check only (see Non-Goals) — it will catch a handler that is pathological from its first call, but not a handler whose cost creeps upward over releases while staying under the ceiling; that would require a persisted baseline, which is parked pending a decision on the maintenance cost of keeping such a baseline current.

### Decision 5: Concurrent multi-device and heterogeneous multi-driver are separate scenarios

Both scenarios share one helper (`_exercise_all_runtime_metrics`) that drives a healthy-load phase followed by a deliberate fault-injection phase against the deferred-command test driver, and both assert the same full metric family. They are kept as two scenarios, not one parameterized over "count", because they stress two different axes of the same shared-context risk: device *count* against one driver (does the shared mutex/heap cope with many callers of the same handler?) versus driver *diversity* (does it cope with many different handlers, each with different allocation and timing profiles, contending at once?). A large device count with one driver cannot exercise the second axis; a fixed small set of distinct drivers cannot exercise the first. Both are needed to validate the shared-context design under realistic conditions, and each is independently useful for isolating a regression to one axis or the other.

### Decision 6: Driver-count scaling stays scoped to load/registry/footprint metrics, deliberately

An earlier version of the driver-count scenario also tried to read runtime metrics (`handler.*`, `mutex.*`, `deferred.*`) off a registry inflated with 100 generated stub drivers. That was unsound: the stubs are inert by construction — matched by device types no commissioned device presents — so their handlers are never invoked, and reading zero/absent runtime metrics off them proves nothing. The scenario is scoped to exactly the metrics inert stubs can meaningfully exercise (load timing, registration count, load failures, heap/GC footprint at registration time). Runtime-metric coverage under a large driver *count* combined with active devices is not attempted here; it would require making the stub drivers minimally functional and matchable, which is blocked upstream (see Open Questions).

### Decision 7: `gcflip.sh` caches by content hash of the installed archive, not a state file

`gcflip.sh status` determines the current DEBUG_GC state by checksumming the currently-installed `libmquickjs.a` and matching it against the cached `on`/`off` archives, rather than writing and trusting a separate state file. This makes the reported state self-correcting: if a build step installs a fresh archive out-of-band, the cache comparison reflects reality on the next check rather than trusting a possibly-stale marker. The trade-off is that a completely unrecognized installed archive (neither cached variant) reports as `unknown` rather than a guessed state — treated as a deliberate "don't guess" choice.

## Risks / Trade-offs

- **`live_bytes` sparsity under `DEBUG_GC off`** → Because sampling is opportunistic and GC is lazy in production-representative builds, `live_bytes` may be absent for long stretches under light load. Every consumer treats its absence as a skip, not a failure, but this means the metric's *availability*, not just its value, is itself workload-dependent — a dashboard or alert built on it needs to account for "no recent sample" as a distinct state from "value is low."
- **`registration.total_ms` / `bundle_load_ms` measure wall time, not CPU time** → Under a loaded host (e.g. CI contention) these could read high without an actual regression. No CPU-time counterpart exists yet.
- **Per-series `heap_delta` ceiling is an absolute check only** → As in Decision 4, a slow per-call creep that stays under the ceiling is invisible to this grading. Flagged as a Non-Goal rather than silently accepted.
- **`gcflip.sh`'s cold-build cost is a real, if small, dependency** → The first flip to an uncached variant clones bellard/mquickjs over the network and builds it (~9 s observed). In an environment without network access or a pre-warmed cache (e.g. certain CI runners), the first flip to a given state will fail or stall rather than degrade gracefully. Mitigation (pre-warming the cache, or baking both variants into the dev container image) is left to the CI-adoption decision, out of scope for this change.
- **Heterogeneous-driver scenario's driver set is capped by what matter.js can commission** → The scenario exercises five distinct real device types (plus the deferred test driver) because that is the practical ceiling given the current test harness; see Open Questions.

## Open Questions

- **Per-driver retained-footprint attribution.** Could a controlled, one-driver-at-a-time isolation sweep (commission driver X alone, drive its representative operations, read the settled `live_bytes` floor, subtract the shared idle baseline to avoid over-counting it once per driver) produce a sound, static, per-driver footprint table analogous to the removed `load.heap_bytes` but built on the sound `live_bytes` mechanism instead of a forced-GC bracket? This would close the *dev-time, static* half of the attribution gap (see Non-Goals) but not runtime, mixed-load attribution, which would need per-allocation accounting or per-driver JS contexts.
- **Feasibility of >5 distinct active drivers for the heterogeneous scenario.** matter.js 0.16.10 bakes each endpoint's device type into its standard device class with no generic/parameterizable device type and no `--device-type` flag; SBMD matches on the endpoint's Descriptor device-type list, not `productDescription`, so a stub device cannot be made to present an arbitrary, SBMD-matchable device type without patching matter.js itself. Whether that patching is worth doing to raise the distinct-active-driver ceiling above the current ~5–7 real device types is unresolved.
- **Whether to recalibrate or accept the current per-series `heap_delta` ceiling values** (`watch` ≥0.8% of arena, `concern` ≥3%) against more workloads before treating them as final.
- **Whether the demand-side (event/throughput rate) and rate-windowed observability gaps identified during this work warrant a follow-on change**, given they represent the largest remaining blind spots for moving from lab characterization to field observability.
