## 2. Core-service support

- [x] 2.1 Resolve the owning device UUID of a device/endpoint/resource/metadata URI with `deviceUriGetDeviceUuid()` in `core/src/device/icDevice.c` (declared in the core-internal `core/src/deviceUri.h`), next to the existing URI helpers
- [x] 2.2 In `subsystemManagerReadyForDevicesCallback()`/`startDeviceInitialization()`, flag devices needing reconfiguration as pending (synchronously scheduling their reconfiguration, decided with the internal `DeviceNeedsReconfiguring(const icDevice *)` on the already-loaded device) before publishing readiness. Readiness is split into `subsystemsReadyForDevices` (internal; used by the startup failure fallback) and `deviceOperationsReady` (returned by `deviceServiceIsReadyForDeviceOperation()`), set after the pass and before driver notification and the ready event. `deviceInitializationTask()` is renamed `DeviceSynchronizationTask()`, since it now only synchronizes. If shutdown begins during the pass, scheduling stops and readiness is not published (checked under `subsystemsAreReadyMutex`); a ready callback arriving after shutdown began is ignored. A failed startup reconfiguration falls back by queuing `DeviceSynchronizationTask()`, which skips drivers without `synchronizeDevice()` (the previous direct call crashed for them) and lets the device stop being pending without waiting for the synchronization.
- [x] 2.3 Startup ordering is unit tested by `deviceServiceReconfigurationTest.c` (4.6); the integration harness cannot re-run startup in-process (see design.md).
- [x] 2.4 Fix pending-state integrity (design.md D8): both cancel paths act only on a successful `cancelDelayTask()` (via `CancelReconfigurationTask()`, which cancels under `ctx->mtx` and releases the returned reference); otherwise the task is told to terminate and, on removal, waited for. `FinishReconfiguration()` clears the task handle under `ctx->mtx`, and so does a successful cancel, so a freed or reused handle is never passed to `bartoncommon` (a second canceller sees no handle and falls back to signal-and-wait). In `deviceServiceReconfigureDevice()`, hold a local reference and hold `ctx->mtx` from before the device becomes pending until the task handle is stored (pre-existing use-after-free/data race when a zero-delay task finishes first, and an unset handle seen by a concurrent removal), clear the pending entry if scheduling fails, and release both references if the map insert is refused (a duplicate, shutdown, or a device being removed, in which case the request is merged with any others and requested again if the removal fails; each reason is logged). A request without a device UUID is refused. A request for a device with no stored record is refused before the insert (after reading the record once more, in case a swap finished meanwhile), and backed out after it if the device was deleted meanwhile; both checks read the database outside the control lock (design.md, Risks). Every request goes through the insert, including one for a device already pending, so a request made during a removal is deferred rather than dropped as a duplicate, including one made while a reconfiguration swaps the device's record. If the removal gave up waiting for a still-running reconfiguration and then fails, the deferred request is dropped with a warning. The map refuses inserts once shutdown begins, and removal deletes only the given context. `cancelPendingReconfigurationTasks()` snapshots contexts under the control lock and works on them after releasing it, so `ctx->mtx` is never taken under that lock. A `device.reconfiguration.pending` gauge reports the pending count.
- [x] 2.5 Emit `device-configuration-completed`/`-failed` (session discovery type `NONE`) when `reconfigureDeviceTask()` finishes, after the device stops being reported as reconfiguring (its context moves from the pending map to a list of finishing reconfigurations, which it leaves after the event), so removal and shutdown wait for the event; skip it for a reconfiguration that finishes after shutdown begins, or if the database no longer has the device's record (`sendDeviceReconfigurationFinishedEvent`). A failed save of the rebuilt device (`finalizeNewDevice()`) makes the reconfiguration a failure. The finishing sequence lives in `FinishReconfiguration()`. The three existing configuration-event senders share one property-setting helper.
- [x] 2.6 `reconfigureDeviceTask()`/`FinishReconfiguration()` and the D8 paths are unit tested by `deviceServiceReconfigurationTest.c` (4.6), using reconfigurations that fail before any driver configuration. No automated test runs a real driver's reconfiguration to completion: in the integration harness that crashes inside the Matter SBMD driver, which is unrelated to this change. The removal cancel path is also covered end to end by 6.3 and the shutdown cancel path by 6.1's teardown, both under ASan.
- [x] 2.7 Make the reconfiguration timed waits block (design.md D8, pre-existing): create the per-context and shared condition variables with `initTimedWaitCond()` (the shared one once, via `pthread_once` in `ReconfigurationControlCond()`), check under the control lock that the context is still pending before each removal wait (`IsReconfigurationContextPendingLocked()`), and bound the shutdown wait by a 120 s deadline instead of a wake-up count. Reproduced with a standalone program (a 1 s wait returned in 8 µs on the default condition variable). The waits for a running task are unit tested (4.6) for blocking until the task finishes and then proceeding promptly; the clock fix itself isn't observable in a test, because a spinning wait meets the same timing assertions.
- [x] 2.8 In a repeated startup pass, skip a device the snapshot says needs reconfiguring if it is already pending (an earlier pass is reconfiguring it), and otherwise re-check it against its current record before scheduling, so an earlier pass's reconfiguration is neither raced by a synchronization nor repeated.
- [x] 2.9 Fix the pre-existing lost quit in `stopMainLoop()` (design.md, unit-test harness risk): quit repeatedly until the event thread reports that its loop returned (a quit queued as a source on the default context could be dispatched first by an application iterating that context), so stopping right after starting no longer blocks forever in `pthread_join()`. A stop made on the event thread itself quits once and detaches it; a repeated stop, or one after the event thread failed to start, returns at once.
- [x] 2.10 Guard the device-synchronization thread pool pointer with a mutex (`QueueDeviceSynchronization()`), so shutdown can't destroy the pool while the startup pass or the startup failure fallback is adding to it.
- [x] 2.11 Make shutdown wait (up to 120 s) for a startup pass in progress, since the pass now runs on the ready-callback thread instead of the thread pool shutdown already waited for; a pass on shutdown's own thread is not waited for. A pass skips any device with a reconfiguration pending, before deciding between reconfiguration and synchronization, and synchronizes it if that reconfiguration fails, unless the device is being removed (as for the startup fallback), in which case only once that removal fails (queued only, never run inline on the removal caller's thread).
- [x] 2.12 Coordinate synchronization with removal and reconfiguration, and harden start/stop: a synchronization registers when it is about to call the driver, and is recorded on a removal in progress or left to a pending reconfiguration instead; removal and reconfiguration tasks wait for one already running. A reconfiguration owing a synchronization (startup, or one a synchronization was left to) passes it on when it fails or is withdrawn (cancelled by a removal, or not scheduled). Shutdown is claimed once, and waits for a readiness notification on another thread before it begins; start returns false if a ready-event handler stopped the service during it; the event loop run is published before its thread starts.

- [x] 4.2 CMocka: another device's reconfiguration and URIs without an owning device (`/`, no leading `/`, `//uuid`) pass through to the backend (`test_b_core_client_uri_gate_passes_other_and_malformed_uris`)
- [x] 4.3 CMocka: `get_devices` ignores the gate and includes a reconfiguring device (`test_b_core_client_get_devices_ignores_gate`; the other list getters have no closed-gate test); writes and executes ignore the gate (`test_b_core_client_write_and_execute_ignore_gate`)
- [x] 4.4 Gating tests reset the mock state in per-test setup (which always runs) and teardown; `setup_b_core_client` reuses the same reset. The reconfiguring mock is keyed by device UUID only
- [x] 4.5 CMocka: `test_sendDeviceReconfigurationFinishedEvent` covers both outcomes, the `NONE` session type, and that nothing is emitted without a device class or UUID
- [x] 4.6 CMocka (`core/test/src/deviceServiceReconfigurationTest.c`): starts the real device service with drivers, subsystems, events and the delayed-task scheduler faked via `--wrap`, devices in the real JSON database in a temporary directory, and scheduled reconfigurations captured rather than run. Covers: devices flagged before readiness is published; readiness withheld when shutdown begins mid-pass (with the insert refused); readiness withdrawn as soon as shutdown begins, and a ready callback during shutdown ignored; completion un-pends before the event, plus the startup failure fallback (also when the thread pool rejects its task); scheduling failure; removal cancelling a not-yet-started reconfiguration; removal and shutdown blocking until a running reconfiguration finishes, with the completion event sent before `device-removed`; a removal that starts while the completion event is being sent waiting for it, and a removal or stop made from the event's own handler not waiting for itself; a reconfiguration requested while the previous one is sending its completion event (from another thread, returning without waiting, or from the event's own handler) being scheduled, with the device reported as pending, one requested while the device is being removed being refused, and requested again if the removal fails; one requested for a device without a record (including from a `device-removed` handler) being refused; one whose record was only briefly missing being scheduled; one for a device deleted between the record check and the insert being backed out; one without a UUID being refused; shutdown started on another thread waiting for a completion event already being sent; shutdown waiting for a startup pass in progress, and a stop from the ready event's handler not waiting for itself; a repeated pass leaving alone a device pending for another reason, and synchronizing it if that reconfiguration fails; a stop from a callback on the event thread, and stopping again after it; a second stop repeating nothing; a stop from a ready-event handler during start; shutdown waiting for a readiness notification in progress; removal and reconfiguration waiting for a running synchronization; a synchronization deferred to a reconfiguration requested after it was queued; synchronization owed by a cancelled or unscheduled reconfiguration; no fallback synchronization for a device being removed, and the skipped one running when the removal fails; no completion event for a device without a stored record; repeated passes skipping pending devices and re-checking the current record; the `device.reconfiguration.pending` gauge rising and falling (only with the `memory` observability backend, the only one that records gauges); a zero-delay task that starts before scheduling returns completing safely; a failed startup reconfiguration for a driver without `synchronizeDevice()`. Synchronization tasks run inline, so assertions that a device was not synchronized are deterministic, and the wait tests run the task only after the remover or shutdown has failed to cancel it. Where a test checks that a thread stays blocked (shutdown's wait, a removal during the completion event), it gives that thread 500 ms to get past the block; only a regression can, so a slow host can at worst miss a regression, never fail a correct build. All other waits are bounded, so a regression fails rather than hangs. The tests were checked to fail when their guarantee is removed from the production code. Not tested: "Same reconfiguration cancelled twice" and "Older reconfiguration finishes after a newer one is scheduled". The first needs a second canceller to take the context in a window that has no hook point; the second can't arise through current code paths, since a context leaves the pending map only when its task finishes or is cancelled, so the identity check is defensive. Also without a deterministic test: "Device removed right after scheduling" (the removal racing the scheduler while it holds `ctx->mtx`; the test removes only after scheduling returns), "Running reconfiguration finishes as a removal starts waiting" (the test doesn't force that ordering), and the reference releases on cancel and on scheduling failure, which only ASan/LeakSanitizer runs check.
