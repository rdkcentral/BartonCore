## Why

The SBMD factory eagerly activates every `.sbmd.js` driver at startup and never deactivates any of them, so each spec on disk costs heap for the process lifetime — even device types that are never discovered. The existing specs (`sbmd-v4-runtime`, `sbmd-system`) already describe a lazy lifecycle (activate on claim, deactivate when the last device is removed, metadata available while inactive), but the implementation never conformed. As the SBMD spec catalog grows to cover more Matter device types, the wasted heap for unused drivers scales linearly.

## What Changes

- Stop activating drivers at startup. `SbmdFactory` loads each `.sbmd.js` file, extracts the claim metadata (name, device types, vendor/product IDs, device class, file path), and registers the driver in an **inactive** state.
- After a driver is loaded and its claim metadata is captured, release the retained spec source text and the heavy parsed registration collections (endpoints, resources, aliases, handler references), keeping only the lightweight **claim metadata** resident.
- Activate a driver on demand: when a device first claims it (via `SpecBasedMatterDeviceDriver::AddDevice`, the single funnel used by both fresh commissioning and post-restart re-synchronization), re-read the spec file **from disk**, re-parse, root the handler JSValues, and build the dispatch tables.
- Deactivate a driver when its **per-driver device count** reaches zero (last device removed), releasing handler GC roots, dispatch tables, source text, and heavy registration back down to its claim metadata.
- Add observability for activation/deactivation events and the current active-driver count.
- Bring the implementation into conformance with the already-specified lazy claiming lifecycle, and extend the lifecycle spec with the memory-reclamation (claim-metadata) and disk-reread semantics.

The memory-reclamation change is **not** a breaking change to the consumer contract: the public API, the claim path (`MatterDriverFactory::GetDriver` / `ClaimDevice`), the `DeviceDriver` C struct, and the driver-manager registration all remain in place and behave identically. What changes is the runtime memory footprint of idle drivers, plus one operational requirement: the configured spec files must stay on disk, unchanged, while Barton runs (see Impact). A companion hardening does tighten a **spec-author-facing contract**. To keep the disk re-read validation sound (see design D4), the loader now **rejects** a `.sbmd.js` spec whose numeric claim/version fields are not integers within their storage ranges — `matter.deviceTypes`/`vendorId`/`productId` must be integers in 0–`0xFFFF`, and `barton.deviceClassVersion`/endpoint `profileVersion` integers in 0–255. Such a spec previously loaded with the value silently wrapped, narrowed, truncated, or coerced; it now fails to load. All in-repo specs still load. Specs can be client-supplied (through the public `sbmd_dirs` initialize parameter), so an affected client spec is handled conservatively: at startup only that driver is **skipped** (not registered, logged, and counted), and SBMD registration as a whole — and therefore the Matter subsystem — still starts. The public API/ABI (soname) is unchanged. The spec-author contract change is signaled where SBMD versions its authoring format: the **SBMD schema version is bumped `5.0` → `5.1`** (`sbmd-spec-schema.json` `const`, enforced by `validate_sbmd_specs`), with the tightening recorded in `core/deviceDrivers/matter/sbmd/schema/CHANGELOG.md`.

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `sbmd-v4-runtime`: Extend the "Driver lifecycle — activate and deactivate" requirement so that deactivation additionally releases the retained spec source text and heavy registration collections down to the minimal claim metadata, and activation re-reads the spec file from disk rather than from an in-memory copy.
- `sbmd-system`: Clarify that the SBMD factory registers drivers in the inactive (claim-metadata-only) state at startup rather than activating them eagerly, and that a driver is activated on first claim and deactivated when its last device is removed.

## Impact

- **Affected layers**: Matter device drivers (`core/deviceDrivers/matter/sbmd/` — `SbmdFactory`, `SbmdDriver`, `SbmdLoader`, `SpecBasedMatterDeviceDriver`), the Matter driver base (`core/deviceDrivers/matter/MatterDeviceDriver` for the last-device-removed hook and a `try_emplace` in `AddDevice`), `MatterDevice` (detaches from its cache under the stack lock on destruction), `DeviceDataCache` (its destructor now tears its `ReadClient` down on the Matter thread), and the Matter subsystem class (`core/src/subsystems/matter/Matter` — non-constructing `IsEventLoopRunning()`/`IsEventLoopThread()` statics and `RunWithStackLock()`, which let a caller exclude Matter-thread callbacks without instantiating the subsystem). No changes to the public API, core services, or persistence.
- **Threading**: Report dispatch reads the registration and dispatch tables on the Matter event loop without the JS mutex, so every step that replaces or frees them — committing an activation, failed-bind teardown, and last-device teardown — holds both the JS mutex and the CHIP stack lock that the event loop holds while dispatching (`Matter::RunWithStackLock()`), or runs on the event loop thread itself. The slow part of activation (spec read, evaluation, validation) runs before that lock is taken. A bind wires a device to the driver only after every rejecting check has passed, and a `MatterDevice` detaches from its data cache under the stack lock when destroyed, so a rejected device never dispatches into the driver. `Matter::IsEventLoopRunning()` reports the event loop thread as gone only after `Stop()` has joined it, and teardown after the JS runtime has shut down detaches handler references instead of touching the freed context. The claim path continues to use only C++ metadata and never triggers JS evaluation.
- **Consumers**: The public API is unchanged, but the change adds one operational requirement on the integrating product: the directories it configures in `sbmd_dirs`, and the `.sbmd.js` files in them, must stay present and unchanged, and readable without stalling, while Barton runs. A driver re-reads its spec from disk whenever it activates, so a spec removed or renamed after startup, or edited in a way that changes its claim identity or versions or makes it invalid, makes later binds to that driver fail (logged and counted in `sbmd.driver.activation.failure`) until the process restarts. Other edits are not rejected: they take effect the next time that driver activates. This requirement is also stated on the public `b_core_initialize_params_container_set_sbmd_dirs` documentation. This is the deliberate trade-off for not keeping every spec in memory (design D3/D4) and is documented in `docs/SBMD.md`.
- **I/O**: One spec-file disk read per driver activation (once per driver until its device count returns to zero). Full re-read/re-parse is accepted for now; caching compiled bytecode is a deliberate follow-up (see Non-goals).
- **Observability**: New metrics for activate/deactivate events, active-driver count, per-activation duration (`sbmd.driver.activation.duration_ms`), and activation failures (`sbmd.driver.activation.failure{driver,reason}`).
- **CMake flags**: Relevant only when `BCORE_MATTER` (and the mquickjs runtime, `BCORE_USE_MQUICKJS`) are enabled; SBMD specs directory is configured via `BARTON_CONFIG_MATTER_SBMD_SPECS_DIR`. Builds without Matter are unaffected.
- **Tests**: Unit coverage in `SbmdDriverTest` (reduce-to-claim-metadata, activate-from-disk round trips, activation-failure reasons, deactivation after runtime shutdown, numeric-field validation including out-of-range, fractional, `NaN`/infinite, and non-number values) and `SbmdLifecycleTest` (`SbmdLifecycleGuardTest` for the in-flight-bind guard, failed-bind rollback, failed-activation abort, and endpoints sharing a profile); integration coverage in `testing/test/sbmd_lazy_activation_test.py` (idle-at-startup, activation on commissioning, deactivation on last-device removal, re-read spec rejection for a removed spec and for changed claim identity or versions, a relative `sbmd_dirs` entry after a working-directory change, and an invalid spec skipped at startup without stopping the Matter subsystem).

## Non-goals

- Caching compiled bytecode (or any parse result) to avoid re-parsing on activation. The first cut re-reads and re-parses from disk; a bytecode/parse cache is a potential future optimization to be evaluated separately.
- Changing the driver-to-device matching semantics, the two-pass (vendor-specific then generic) claim ordering, or the `DeviceDriver` C struct / driver-manager registration model (the "Tier 3" fully-lazy instantiation approach is explicitly out of scope).
- Any change to non-SBMD drivers (native Zigbee, philipsHue) or to non-Matter subsystems.
