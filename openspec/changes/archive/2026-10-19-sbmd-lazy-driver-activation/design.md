## Context

The SBMD subsystem loads every `.sbmd.js` spec at startup. Today `SbmdFactory::RegisterDriversFromDirectory` reads each file, parses it into an `SbmdRegistration`, wraps it in an `SbmdDriver`, calls `Activate()` immediately, wraps that in a `SpecBasedMatterDeviceDriver`, and registers it with `MatterDriverFactory` and the `deviceDriverManager`. Every driver therefore holds, for the process lifetime: the parsed registration (endpoints/resources/aliases/handlers), the retained spec source text (the dominant cost, ~10–50 KB per spec), rooted handler JSValues in the shared mquickjs heap, and built dispatch tables.

The `SbmdDriver` class already implements an `Activate()` / `Deactivate()` / `IsActivated()` lifecycle:
- **Load** produces metadata + registration; the loader roots each handler JSValue as it extracts it (so a loaded registration owns GC roots until they are released).
- **Activate** re-evaluates the source (from an in-memory copy), takes fresh roots on the re-extracted handlers, and builds dispatch tables.
- **Deactivate** releases the rooted JSValues and clears dispatch tables.

The existing specs (`sbmd-v4-runtime`, `sbmd-system`) already state that claiming must not require activation, that a matching driver is activated on claim, and that a driver is deactivated when its last device is removed. **The implementation never conformed** — `Activate()` is only ever called eagerly at startup, and `Deactivate()` is only ever called from unit tests. This change makes the implementation conform and extends the idle footprint reclamation.

**Constraints:**
- `SbmdDriver::Activate()` / `Deactivate()` require the caller to hold `MQuickJsRuntime::GetMutex()`.
- Claiming (`MatterDriverFactory::GetDriver` → `ClaimDevice`) runs on the Matter thread and must use only C++ metadata.
- `SpecBasedMatterDeviceDriver::AddDevice` is the single funnel reached by both fresh commissioning (`CommissioningOrchestrator`) and post-restart re-synchronization (`ConfigureDevice`/`SynchronizeDevice` → `AddDeviceIfRequired`).
- Per-driver device tracking already exists: `MatterDeviceDriver::devices` (map keyed by UUID) guarded by `devicesMutex`.

```
                         ┌─────────────────────────────────────────┐
                         │              Matter subsystem            │
                         └─────────────────────────────────────────┘
   startup                         claim (metadata only)         device bind / unbind
      │                                    │                             │
      ▼                                    ▼                             ▼
┌───────────────┐   register    ┌──────────────────────┐   Add/Remove  ┌──────────────────────┐
│  SbmdFactory  │──────────────▶│  MatterDriverFactory  │──────────────▶│ SpecBasedMatterDevice │
│  (load only)  │   inactive    │  GetDriver/ClaimDevice │              │ Driver (activate hook)│
└───────────────┘               └──────────────────────┘               └──────────┬───────────┘
      │ load, reduce to claim metadata,                                                        │ Activate()/Deactivate()
      │ release source+registration                                               ▼   (under JS mutex)
      ▼                                                                     ┌──────────────┐
  claim metadata resident ◀──────────── Deactivate (last device) ──────────│  SbmdDriver  │
  (name, deviceTypes,                                                       │ active⇄reduced│
   vendor/product, class, path)  ─────── Activate (first device) ─────────▶ └──────────────┘
                                          reads spec file from disk
```

## Goals / Non-Goals

**Goals:**
- Unused (unclaimed) SBMD specs hold only their small claim metadata at steady state — no source text, no heavy registration, no rooted JSValues, no dispatch tables.
- Drivers activate on first device bind and deactivate when their last device is removed, matching the existing spec.
- Preserve all existing behavior: claiming/priority, endpoint resolution, resource binding, read/write/execute, dispatch, deferred operations, prerequisites.
- Add observability for activate/deactivate and the active-driver count.

**Non-Goals:**
- Caching compiled bytecode or parse results to speed re-activation (explicit follow-up).
- Deferring creation of the `SpecBasedMatterDeviceDriver` / `DeviceDriver` C struct / driver-manager entry until claim ("Tier 3" fully-lazy instantiation).
- Any change to non-SBMD drivers, non-Matter subsystems, the public GObject API, or the persistence format.

## Decisions

### D1 — Activation hook: top of `SpecBasedMatterDeviceDriver::AddDevice`
`AddDevice` is the single point that both commissioning and restart re-sync pass through, and it already needs an active driver (it reads `GetCommandDispatch()`/`GetRegistration()`). Activate at the very top of the override, before any registration access, under the JS mutex and serialized with report dispatch (see D5); make it idempotent so repeated binds are no-ops.

*Alternatives considered:* Activating inside `ClaimDevice` — rejected: claiming must stay metadata-only per spec, and a claim does not guarantee a bind. Activating in `ConfigureDevice`/`SynchronizeDevice` individually — rejected: two entry points instead of one funnel, easy to miss a path.

### D2 — Deactivation hook: last-device-removed, driven by per-driver count
Deactivate when the driver's `devices` map becomes empty after removal. Rather than duplicate `MatterDeviceDriver::DeviceRemoved`, add a protected virtual hook (e.g. `OnLastDeviceRemoved()`) that the base invokes after erasing the device under `devicesMutex` when the map is empty; `SpecBasedMatterDeviceDriver` overrides it to deactivate under the JS mutex. Base default is a no-op, so non-SBMD drivers are unaffected.

*Alternatives considered:* Overriding `DeviceRemoved` entirely in the SBMD driver — rejected: duplicates fabric-removal/cleanup logic and risks drift. Reference-counting separate from the `devices` map — rejected: redundant with existing per-driver tracking.

### D3 — Reduce `SbmdDriver`'s registration to its claim metadata when inactive
`SbmdDriver` keeps its `SbmdRegistration` object for its whole lifetime, but while inactive the registration is reduced to its claim metadata: only the fields used for claiming remain populated — `name`, `filePath`, `barton.deviceClass`, and `matter.deviceTypes`/`vendorId`/`productId`. Deactivation (and the load-time `ReduceToClaimMetadata()`) release the `source` string, the heavy parsed collections (endpoints, aliases, handler vectors), the dispatch tables, and every non-claim metadata field (`schemaVersion`, `driverVersion`, `deviceClassVersion`, `matter.revision`, `featureClusters`, `defaultTimeoutMs`, `reporting`) — swap-with-empty releases the vector capacity. `Activate()` replaces the `SbmdRegistration` object wholesale with the freshly parsed one, so the claim-time metadata accessors (`GetSupportedDeviceTypes`, `GetSupportedVendorId`, `GetSupportedProductId`, `IsVendorSpecificDriver`) must **not** read the live registration — a claim-time caller runs without the JS mutex and could dereference the object mid-swap. The accessors therefore read the immutable spec snapshot that the `SbmdDriver` constructor takes (see D4); activation rejects any re-read spec whose claim identity or versions changed, so the snapshot never goes stale. Activation reads the spec file from `filePath` on disk (`ReadSpecFile()`), parses it (`LoadForActivation()`), then swaps in the full registration (`CommitActivation()`).

*Alternatives considered:* A separate `SbmdClaimStub` struct that backs the accessors — rejected: keeping the reduced `SbmdRegistration` avoids a parallel registration type and reduces to the same resident footprint. (The claim-time accessors read a small immutable spec snapshot instead, for thread safety; see above and D4.) Keeping the full registration but only dropping JSValues ("Tier 1") — rejected: leaves the dominant source-text and registration cost resident, failing the goal. Keeping `source` in memory and re-parsing from it — rejected: `source` is the biggest single cost we want to shed.

### D4 — Disk re-read on activation, with claim-identity validation
Activation obtains the spec content by re-reading `filePath` from disk (`EnsureActivated()` reads it before taking the JS mutex and passes the text to `SbmdDriver::LoadForActivation()`) whenever the retained `source` has been released (which it always has in the production flow, since the factory reduces every driver to its claim metadata right after registration). A driver not yet reduced that still holds its `source` re-evaluates that copy instead — this keeps unit tests that load from an in-memory string working. Load-time records `filePath` as an absolute path: the factory resolves each configured `sbmd_dirs` entry to an absolute path once, before reading it, and the `SbmdDriver` constructor makes the recorded path absolute too (by prepending the working directory only; normalizing `..` away textually would change which file a path through a symlinked directory names). Before this change a spec was read only at startup, so a relative `sbmd_dirs` entry was resolved once against the startup working directory; now the file is re-read at bind time, possibly long after startup, and a relative path would resolve against whatever the working directory is then (a host process that changes directory would make every activation fail). Recording the absolute path at load keeps the re-read pointing at the same file the factory loaded. Guard file-read failure: log and fail activation so the bind fails cleanly rather than dispatching against a half-built driver. Because activation runs while Matter-thread dispatch may be waiting on the JS mutex, it guards against a re-read spec that would hold that mutex indefinitely through a realistic mistake:
- `SbmdDriver::ReadSpecFile()` (shared with the startup load) opens the file non-blocking and accepts only a regular file, checked on the opened descriptor, so a spec path that is a FIFO or device cannot block the reading thread (startup, or a binding thread during activation). A file too large to allocate a buffer for fails the read (`ReadSpecFile()` returns false) instead of throwing. `LoadForActivation()` does no file I/O; it takes the text its caller read, or null if that read failed.
- Evaluation and extraction run under the same script deadline as handler calls (`BARTON_CONFIG_SBMD_SCRIPT_TIMEOUT_MS`). A timeout anywhere in the load fails activation with `load_failed`, discards whatever was extracted (an interrupted property read during extraction looks like an absent property, so a partial registration must not be accepted), and clears the pending exception. Because the engine checks the deadline only periodically, each further call into spec code after it fires still runs for a while, so the loader's loops stop as soon as the deadline has fired rather than continuing through the rest of the spec.

The startup load keeps its existing behavior (no script deadline): it runs before the Matter event loop starts, so it cannot stall dispatch.

These guards target realistic mistakes in a spec file, such as an accidental edit that leaves an infinite loop or a spec path that is not a regular file. Spec files are trusted inputs: Barton ships them, or the integrating product installs them in its configured `sbmd_dirs`, and their handlers already run arbitrary JavaScript. This change does not defend against a spec deliberately written to misbehave. In particular, the script deadline interrupts script execution but not a single long-running built-in call (for example sorting a very large array), exactly as for handler calls; that engine limitation predates this change and is tracked separately.

After re-parsing, validate the re-read spec against the claim metadata before going active: compare the claim-identity fields (name, `matter.deviceTypes`, `vendorId`, `productId`, device class). On any mismatch, fail activation, log, and abort the bind. This is scoped to the fields that drove the claim decision — not a deep structural diff — so cosmetic edits to handlers do not falsely reject, but a spec that no longer matches what claimed the device can never dispatch against it.

Separately, the `SbmdDriver` constructor takes a spec snapshot (`SbmdDriver::SpecSnapshot`): the claim fields that claim-time callers read (device types, vendor/product IDs) and the versions published to the device-service layer for commissioning/reconfiguration (the device-class version, and one version per endpoint profile). It is never modified, so `SpecBasedMatterDeviceDriver` reads its claim-time accessors from it without the JS mutex, and its constructor publishes `endpointProfileVersions` from it. `LoadForActivation()` checks a re-read spec against both the claim metadata (`ClaimMismatch`) and the snapshot's versions (`VersionMismatch`), so one place validates a re-read spec, and the device-service layer never publishes/compares a version that disagrees with the handlers now running. The snapshot keeps one version per profile name (the first endpoint declaring it), in declaration order, so the check compares exactly that endpoint's version for each profile, whatever order the profiles appear in; comparing every endpoint would reject a spec whose endpoints share a profile at different versions, which registered and bound fine before this change. The check compares the complete snapshot and re-read profile sets, not just the profiles the re-read spec still declares: a profile *removed* on disk would otherwise pass while `endpointProfileVersions` keeps advertising its startup version to the device-service layer, so a differing profile set (added or removed) is rejected too. Versions are compared at full width; the loader already rejects a `profileVersion` above 255, so the 8-bit published value never narrows.

The same reasoning applies to every numeric claim/version field that is stored narrower than the JS number it is read from, so the rejection is enforced uniformly at **parse time** (not only on re-read): `matter.deviceTypes`, `vendorId`, and `productId` must fit `uint16`, and `barton.deviceClassVersion` and endpoint `profileVersion` must fit `uint8`. The loader accepts only a JS number that is finite, has no fractional part, and lies in range (negative zero is the integer 0); it rejects everything else — out-of-range, fractional, `NaN`/infinite, and non-numbers such as strings, booleans, or `null` (including `null` array elements, and a `deviceTypes` that is not an array), all of which a numeric conversion would otherwise wrap, narrow, truncate, or coerce into an in-range value, or which the loader previously treated as "not set" (`vendorId: null` would silently have turned a vendor-specific driver generic). Only an absent optional field means "not set". So neither the claim-identity comparison nor the version comparison can be defeated by an aliasing value, and the authoring-time schema (`sbmd-spec-schema.json`, enforced by `validate_sbmd_specs`) encodes the same `integer` type and bounds.

At startup, a spec rejected only for such a field is **skipped**: the factory does not register that driver, logs the error, and counts `sbmd.driver.load.failure{reason="invalid_field"}`, but it does not fail SBMD driver registration as a whole. Any other load failure keeps the pre-existing policy (registration fails and the Matter subsystem does not start). The distinction matters because these values loaded before this change (silently truncated), and specs are client-suppliable through the public `sbmd_dirs` initialize parameter; one such spec must not take every Matter device down after an upgrade. `SbmdLoader::LoadDriver()` reports the reason through an `SbmdLoadFailure` out-parameter so the factory can tell this case apart. *Alternatives considered:* widening the stored fields to `uint32` and comparing at full width — rejected: every one of these fields is consumed downstream as `uint16`/`uint8` (e.g. the `DeviceDriver` C struct stores `deviceClassVersion` as `uint8_t`), so an out-of-range value is already meaningless once published; rejecting at parse is more honest than silently truncating. A consequence is that SBMD accepts only `uint16` Matter device types, whereas Matter device-type IDs are formally 32-bit (vendor-prefixed, e.g. `0xFFF1_xxxx`); this matches the pre-existing storage width but narrows what loads — see Open Questions below.

*Alternatives considered:* Trust the file without validation — rejected: a silently-diverged spec could bind handlers inconsistent with the claim. Compare a whole-file hash captured at load — rejected: rejects benign whitespace/comment edits and couples activation to byte-exactness rather than the claim contract.

### D5 — Thread safety
Report dispatch (`HandleAttributeReport`, `HandleEvent`, `HandleCommand`) runs on the Matter event loop and reads the registration and the dispatch tables **without** the JS mutex: it checks `IsActivated()`, then `Lookup()`s raw `DispatchEntry*` pointers that it keeps using across supplement prefetch before taking the JS mutex for the call. So the JS mutex alone cannot make a lifecycle transition safe — committing an activation replaces the registration object and rebuilds the tables, and `Deactivate()` frees them. Every step that replaces or frees that state therefore also excludes dispatch, via `Matter::RunWithStackLock()`:
- The Matter event loop runs every callback (report dispatch, cache callbacks, incoming commands, scheduled work) with the CHIP stack lock held, and the codebase already sanctions `LockChipStack()` as a protected stack context. `RunWithStackLock()` takes that lock (`chip::DeviceLayer::StackLock`) on the calling thread, so the work cannot overlap any of those callbacks, without depending on the loop to *run* anything. This matters because the CHIP loop does not drain queued work when it stops: marshaling onto the loop (`RunOnMatterSync`) can wait forever if `Stop()` lands between its "running" check and the loop running the work.
- On the event loop thread itself (for example the last-device hook, which runs inside `DeviceRemoved`'s Matter-loop work), the work runs directly. That thread is identified by `Matter::IsEventLoopThread()`, which compares against the event loop thread's id recorded by `Matter`. `PlatformMgr().IsChipStackLockedByCurrentThread()` is not used for this: the SDK reports it as true for **every** thread once the loop has stopped, including while the event loop thread is still running shutdown work under the lock.
- If the event loop thread does not exist, nothing can dispatch, so the work runs directly. `Matter::IsEventLoopRunning()` is a non-constructing static that is set in `Start()` and cleared in `Stop()` only **after** the loop thread has been joined, so "not running" really means no Matter-thread callback can be executing. It never instantiates the singleton, so a bind's exit path in a unit test (no Matter stack) does not construct the subsystem.

Activation is split so that the slow part does not hold the stack lock. `EnsureActivated()` first reads the spec file without holding any lock, then loads it under the JS mutex alone (`SbmdDriver::LoadForActivation()`: JS evaluation, claim-identity and version checks). Only then does it commit (`SbmdDriver::CommitActivation()`: swap the registration, root handlers, build the tables) under `RunWithStackLock()` and the JS mutex. A spec that fails either check is discarded before it is ever committed, so there is no rollback of an unvalidated activation, and a concurrent binder that observes `IsActivated() == true` only ever sees a validated registration. If another bind committed first, the second fresh registration is discarded. If the JS runtime was shut down between the two phases, the fresh registration's handler roots are detached rather than released through the freed context, and activation fails with `runtime_unavailable`.

Lock order is `CHIP stack lock → JS mutex → devicesMutex`, matching the Matter thread's own order (dispatch holds the stack lock and takes the JS mutex, and `GetDevice()` takes `devicesMutex`). No code takes the stack lock while holding the JS mutex or `devicesMutex`. In particular `MatterDeviceDriver::AddDevice()` uses `try_emplace`, so a device rejected as a duplicate is destroyed after `devicesMutex` is released rather than inside it (`~MatterDevice` takes the stack lock, see below). A bind waits on the stack lock while `CommissioningOrchestrator::Pair` holds the orchestrator's `mtx`; that cannot deadlock, because the only Matter-thread code that takes `mtx` is the orchestrator's own discovery/pairing delegate callbacks, which are registered only during `Commission()` and unregistered before `Pair()` runs (and never registered on the direct `Pair()` path). The successful bind path already waits on the Matter thread under `mtx` (via `deviceServiceDeviceFound`), so this introduces no new wait-under-`mtx` pattern.

A bind wires the device to the driver (attribute/event/command callbacks, incoming command handlers) only after every check that can reject it has passed — endpoint resolution and prerequisites — and does the wiring under `RunWithStackLock()`, since the device's cache delivers those callbacks on the event loop and registering CHIP command handlers requires the lock. A rejected device therefore never has callbacks that can dispatch into the driver. Separately, `~MatterDevice` detaches from its data cache and unregisters its command handlers under `RunWithStackLock()`. Before this change the device was destroyed off the Matter thread only on rare paths; a rejected bind now does it routinely, and a cache callback (such as subscription-established) could otherwise still be running into the device as it is destroyed.

The same timing exposed a race in `~DeviceDataCache`, which used to `release()` its `ReadClient` on the calling thread before scheduling the deletion on the Matter thread, so a subscription callback running there could dereference a null `readClient`. The destructor now resets both pointers on the Matter thread itself (it already waited for that work), so a callback sees either the live client or none. (Its remaining reliance on `IsChipStackLockedByCurrentThread()`, which is true on every thread once the loop has stopped, predates this change and is tracked separately.)

Last-device teardown and failed-bind rollback share one primitive, `DeactivateIfIdle()` (caller holds the JS mutex and is serialized with dispatch): it deactivates only when the driver is still activated, no bind is in flight (a per-driver in-flight-bind counter is zero), and the device map is empty when rechecked under `devicesMutex`. The last-device hook and every `AddDevice` exit (`~InFlightBind` → `TeardownIfIdle()` → `RunWithStackLock()`) both funnel through it, so a bind that activated the driver and then failed rolls back only when nothing else relies on the activation, and a teardown deferred because a bind was racing is retried when that bind finishes and leaves the driver idle. The destructor swallows any teardown exception so it can never escape a `noexcept` destructor.

A bind can still fail after `Matter::Stop()` has shut the JS runtime down and freed its context. Activation therefore refuses a null context, and `Deactivate()` given a null context detaches the handler references instead of releasing them through the freed context (as `~SbmdDriver` already did).

Deferred operations park a promise owned by `ConnectAndExecute`'s local list, which is freed if `ConnectAndExecute` stops waiting. The new last-device `CancelAllPendingOperations()` completes such operations even when no device response will ever arrive, so the parking promise is registered with `AssociateStoredContext()` and completed through `FinalizeStoredContext()`; `ConnectAndExecute` invalidates it on exit, making a late completion a no-op instead of a write to a freed promise. (The stored-context set is keyed by address, so a later operation's promise reusing that address could still receive a stale completion; that limitation of the existing mechanism is tracked separately.)

This protocol is covered deterministically by unit tests (`SbmdLifecycleGuardTest`): with a bind marked in flight `OnLastDeviceRemoved()` defers teardown; once the in-flight count returns to zero `DeactivateIfIdle()` retries it; a bound device keeps the driver active; a bind that activates then fails is rolled back; a failed activation aborts the bind; and a spec whose endpoints share a profile at different versions binds. `SbmdDriverTest` covers deactivation after the runtime has shut down. The cross-thread exclusion itself relies on the CHIP stack lock.

### D6 — Observability
Add metrics, gated by `BARTON_CONFIG_SBMD_METRICS`, following the existing observability helpers:
- Attributed activate/deactivate event counters (`ObservabilityCounter` with a driver-stem attribute) for churn and per-driver attribution.
- A current active-driver count as a synchronous `ObservabilityGauge` **set to the live count on each activate/deactivate transition**, mirroring the existing `registeredDriversGauge` / `RecordRegisteredDriverCount` pattern. The factory also publishes this gauge once after startup registration (counting `IsActivated()` drivers — normally zero), so the gauge reflects true startup state rather than being absent until the first bind.
- A per-activation duration histogram (`sbmd.driver.activation.duration_ms`) recorded on demand from the start of loading the spec until the activation is committed (`SpecBasedMatterDeviceDriver::EnsureActivated()`), separate from the startup `sbmd.driver.load.duration_ms` (now load-and-register only).
- An activation-failure counter (`sbmd.driver.activation.failure`) with `driver` and `reason` attributes, so a device that silently stops binding after a spec drift is visible in telemetry rather than only in logs. The reasons distinguish the causes an operator would act on differently: `read_failed` (spec file unreadable), `invalid_field` (a numeric claim/version field is not an integer in range), `load_failed` (spec not evaluable), `claim_mismatch` (claim identity changed on disk), `version_mismatch` (device-class/profile version or set changed), and `runtime_unavailable` (JS runtime shut down). `SbmdDriver::LoadForActivation()` reports `read_failed`, `invalid_field`, `load_failed`, `claim_mismatch`, `version_mismatch`, and `runtime_unavailable` (null context) through an `ActivationFailure` out-parameter, and `runtime_unavailable` also covers a runtime shut down between loading and committing.
- A load-failure reason `invalid_field` for a spec skipped at startup (see D4). The old load-time `reason="activation_failed"` is retired, since activation no longer runs at load.

The active-count gauge and event counters live in the SBMD driver metrics owned by the activation path (`SpecBasedMatterDeviceDriver`); the process-wide active count is maintained as the drivers transition.

*Alternatives considered:* Deriving the current active count by subtracting two monotonic counters (activations − deactivations) — rejected: harder to dashboard, can drift, and the codebase already has a set-on-change gauge idiom.

## Risks / Trade-offs

- **[Re-parse cost on every activation]** → Activation now does a disk read + full parse instead of reusing an in-memory copy. This occurs once per driver until its device count returns to zero, on an already-async commissioning/sync path; acceptable. There is no deactivation hysteresis, so a device that repeatedly flaps off and back on re-parses the spec each cycle; device removal is infrequent and the parse stays on the async path, so this is accepted. Bytecode caching is the documented follow-up if either ever matters.
- **[Spec file changed or removed on disk after startup]** → Activation reads the live file, which could differ from what was loaded at startup. Mitigation (decided, see D4): treat read/parse failure as an activation failure, and validate the re-read spec's claim-identity fields against the claim metadata, rejecting on mismatch (bind fails, logged). Edits that keep the claim identity and versions (handler code, aliases, resources) are not rejected: they take effect the next time the driver activates, while an already-active driver keeps the version it loaded. This is an unsupported side effect, not a live-reload feature; the documented requirement is that spec files stay unchanged while Barton runs.
- **[A dispatch or resource path that assumes always-active]** → Any code reading the heavy `GetRegistration()` collections (or `reporting`) while inactive would be unsafe. Mitigation: audit all `GetRegistration()`/dispatch callers; the dispatch entry points already gate on `IsActivated()`, and `GetDesiredSubscriptionIntervalSecs()` falls back to the base default when inactive rather than reading the zeroed `reporting`. The claim-time metadata accessors read the immutable spec snapshot (D4), never the registration.
- **[Re-entering the Matter loop during last-device teardown]** → `OnLastDeviceRemoved()` runs inside `DeviceRemoved`'s `RunOnMatterSync` block, so anything it calls that re-enters the Matter loop (nested `RunOnMatterSync`/`ConnectAndExecute`) would self-deadlock. Mitigation: the hook is documented as Matter-loop-reentrant-forbidden, and `CancelAllPendingOperations()` only settles promises and releases JS roots (no Matter-loop work).
- **[Concurrent bind/remove racing activation state]** → `AddDevice` activates the driver (on the commissioning thread) before it inserts into the `devices` map, so the empty-map observation that triggers `OnLastDeviceRemoved()` (on the Matter thread) can go stale, a rollback of a failed bind can collide with another bind that adopted the activation, and a teardown deferred during an in-flight bind can be lost. Mitigation: a per-driver in-flight-bind counter (held across the whole of `AddDevice`) plus the single `DeactivateIfIdle()` teardown primitive — shared by the removal hook and every `AddDevice` exit — that deactivates only when the driver is still activated, the counter is zero, **and** the device map is still empty when rechecked under `devicesMutex`. The re-read spec is validated before it is committed (D5), so an active driver is always validated. Every step that replaces or frees the registration or dispatch tables also holds the CHIP stack lock (D5), so it cannot overlap report dispatch, which reads them without the JS mutex. Committing is skipped if another bind already activated the driver, `Deactivate()` remains idempotent, the counter is a lock-free atomic, and the recheck takes only the leaf `devicesMutex`.
- **[Activation evaluates a spec while holding the JS mutex]** → The disk read happens before the JS mutex is taken (`EnsureActivated()` reads the file with `ReadSpecFile()` and passes the text to `LoadForActivation()`), so slow client storage cannot hold the mutex; a read that fails (including a file too large to allocate) is reported as `read_failed` without being retried under the mutex. JS evaluation (typically tens of milliseconds) does run under the JS mutex but not the stack lock, so the Matter event loop keeps running; report dispatch for other drivers waits on the JS mutex for that long, as it already does for any handler call. Only the commit (a pointer swap, rooting handlers, building the tables) holds the stack lock. Measured on a debug, AddressSanitizer-instrumented dev-host build: activating the temperature-sensor driver took about 18 ms in total, of which the commit was under 1 ms; evaluating the largest specs at startup took about 170 ms (thermostat) and 230 ms (camera), which bounds how long a first bind can hold the JS mutex on that host. Target hardware is slower and has not been measured; bytecode caching (the documented follow-up) is the remedy if this matters there.
- **[A spec read that never returns]** → The read before the JS mutex holds no lock, but it runs on the binding thread inside `AddDevice()`. If the client's storage stalls a regular-file read indefinitely (for example, a hung network mount), that commissioning, `configureDevice`, or `synchronizeDevice` call never completes, and the driver cannot deactivate while that bind is in flight. Report dispatch and the Matter event loop keep running, but the stall can spread beyond that one driver: device synchronization after a restart runs on device service's shared pool of 5 threads, so stalled binds can occupy every thread and stop all devices of every driver from being synchronized, and device-service shutdown waits for that pool, so it hangs too. Barton cannot bound a blocking `read(2)` on a regular file without a separate reader thread, so this is an accepted trade-off: configured spec storage must answer reads promptly, as it already must for the startup load, which blocks device-service initialization on the same reads.
- **[Deactivation while an in-flight deferred operation is outstanding]** → A deferred op holds handler `SafeJSValue` roots and could complete after the last device is removed, dispatching against an inactive driver and blocking root reclamation. Mitigation (implemented): `OnLastDeviceRemoved()` calls `CancelAllPendingOperations()` — completing every outstanding deferred op as a failure and releasing its handler roots — before taking the JS mutex and deactivating.

## Migration Plan

- No public API, GIR, signal, property, or persistence-format change, so no code migration is required. The integrating product must keep its configured `sbmd_dirs` and their spec files present, unchanged, and promptly readable while Barton runs (see the proposal's Impact section).
- **Spec authors** must ensure numeric claim/version fields are integers within their ranges: 0–`0xFFFF` for `matter.deviceTypes`/`vendorId`/`productId`, 0–255 for `barton.deviceClassVersion`/endpoint `profileVersion`. A spec with any other value — previously accepted and silently wrapped, truncated, or coerced — now fails to load: at startup only that driver is skipped (the rest of the Matter subsystem starts normally), and it must be corrected. The build-time schema (`sbmd-spec-schema.json`) and the `validate_sbmd_specs` target flag these before runtime, and the loader logs an explanatory error and counts `sbmd.driver.load.failure{reason="invalid_field"}`.
- Land behind the existing `BCORE_MATTER` build; no new CMake flag.
- Rollback is a straight revert — no on-disk state is written or migrated. If a runtime escape hatch is desired for triaging, an optional config/env toggle could force eager activation at startup (retaining old behavior), but it is not required.

## Open Questions

_Resolved:_
- **Activation validates the re-read spec against the claim metadata and rejects on mismatch** (claim-identity fields only). See D4.
- **Active-driver count is a set-on-change `ObservabilityGauge`** (mirroring `registeredDriversGauge`), alongside attributed activate/deactivate counters. See D6.
- **How the spec-author contract tightening is versioned.** It is signaled via the SBMD schema version, bumped `5.0` → `5.1` and recorded in `schema/CHANGELOG.md`. The public API/ABI (soname) is unchanged. Clients can supply spec directories (`sbmd_dirs`), so a client spec with an invalid value is affected; that driver is skipped at startup rather than failing the Matter subsystem (see D4), so no consumer loses its other devices.
- **Can a bind that blocks on the Matter thread deadlock with `CommissioningOrchestrator::Pair`'s lock?** No. See D5: the only Matter-thread code that takes that lock is the orchestrator's own delegate callbacks, which are unregistered before `Pair()` runs.
- **Are specs whose endpoints share a profile at different versions supported?** They registered and bound before this change, so they must keep binding. The activation-time version check compares only the version the spec snapshot keeps for each profile (D4).
- **`uint16`-only `matter.deviceTypes`.** Matter device-type IDs are formally 32-bit (vendor-prefixed, e.g. `0xFFF1_xxxx`), but Barton's claim path has never supported them: `DeviceDataCache::GetDeviceTypes` truncates a device's reported type to 16 bits, `GetSupportedDeviceTypes()` and endpoint resolution take `uint16_t`, and the loader truncated spec values before this change. Keeping the 5.1 rejection (see D4) therefore removes no working capability; it makes a spec that asks for a 32-bit type fail loudly instead of silently matching a truncated value. Supporting 32-bit device types would mean widening that whole path and is not planned.
